# GlobeTrotter — Integration Rulebook

**Read this before writing a single line of UI.** It exists because the
build order changed, and that change moved where the risk lives.

## 0. What changed, and why this document exists

The original plan (see `TASKS.md` history) ran Backend and Frontend in
parallel, integrating continuously at a Wave 1 checkpoint. The team has
since chosen a different order:

> **Phase A** — finish the *entire* backend, all waves.
> **Phase B** — generate the *entire* UI in **Stitch**, then port it into React.
> **Phase C** — join the two.

That is a legitimate call — Stitch produces a far more polished UI than
hand-built React under time pressure, and generating all screens in one
pass keeps them visually consistent. But it trades away the thing
continuous integration was buying: **early, cheap discovery of mismatches.**
In the parallel plan, a wrong field name surfaced on day one. In the
sequential plan, it surfaces during Phase C, which is also the moment
before the demo, and the moment with the least time to fix anything.

So the integration risk is not lower — it is *deferred and concentrated*.
Every rule below exists to make Phase C mechanical instead of exploratory.
The core idea:

> **The API contract is frozen, machine-readable, and generates the
> frontend's types. Stitch contributes pixels; it never contributes data
> shapes, field names, routes, or fetch code.**

If that holds, Phase C is "paste markup, swap placeholder data for a typed
API call, done" — not "discover the backend calls it `date_start` and the
mock calls it `startDate`, across 15 screens."

## 1. The contract pipeline

```
backend/app/**          ← single source of truth (routes + Pydantic schemas)
        │  python export_openapi.py
        ▼
contract/openapi.json   ← frozen, committed snapshot of the live API
        │  npm run gen:types
        ▼
frontend/src/types/api.d.ts     ← AUTO-GENERATED. Never hand-edit.
        │
        ▼
frontend/src/types/models.ts    ← friendly aliases (Trip, Stop, Budget, ...)
frontend/src/api/client.ts      ← the ONE fetch boundary
frontend/src/api/endpoints.ts   ← one function per route
        │
        ▼
Stitch-derived screens          ← import types + call endpoints. Nothing else.
```

**After any backend route/schema change, both commands run, in this order:**

```bash
cd backend && python export_openapi.py && cd ../frontend && npm run gen:types && npm run typecheck
```

A field the backend does not return cannot exist in the frontend's types.
A screen that reads it fails `npm run typecheck` — at build time, on
someone's laptop, minutes after the change. That is the entire mechanism,
and it is why `contract/openapi.json` is committed rather than generated at
runtime: a committed snapshot makes contract drift show up as a reviewable
diff.

## 2. Non-negotiables

1. **`api.d.ts` is generated.** Hand-editing it silently decouples the
   frontend from the backend and defeats everything above.
2. **Nothing outside `client.ts` calls `fetch`.** Not a component, not a
   hook, not a Stitch paste-in.
3. **No URL path string outside `endpoints.ts`.**
4. **No screen re-declares an API shape.** Import from `types/models.ts`.
   If the type you need isn't there, add an alias there — don't write a
   local `interface Trip`.
5. **The backend is the source of truth for names.** When Stitch calls it
   `startDate` and the API calls it `date_start`, the API wins and the
   component adapts. Never rename server-side to match a mock.
6. **`contract/openapi.json` is committed** and regenerated by the script,
   never edited by hand.

## 3. Known conflict traps

These are the specific mismatches that would otherwise be found at 2am on
demo day. Each one is already handled in `client.ts` / `models.ts` — this
section says *why*, so nobody "simplifies" the handling away.

### 3.1 Money is a JSON **string**, not a number

Pydantic serializes `Numeric(10,2)` / `Decimal` as a **string**:

```json
{ "amount_total": "70.00", "amount_per_day": "5.00" }
```

This is correct and deliberate — CONTRACTS §8 keeps money exact and refuses
`Float`, and a JSON number would reintroduce binary-float rounding. But it
means:

```ts
budget.amount_total + 5        // ❌ "70.005"  — string concatenation
Number(budget.amount_total) + 5 // ✅ 75
```

Use `formatMoney()` from `types/models.ts` for display. Never do arithmetic
on the raw value, and never send a rounded number back to the server.

### 3.2 Dates are `YYYY-MM-DD` strings, not `Date` objects

`date_start`, `date_end`, `scheduled_date` are plain ISO date strings with
no time and no timezone (CONTRACTS §8). They sort correctly as strings.
Do **not** wrap them in `new Date()` for comparison or display without
being deliberate — `new Date("2026-06-01")` parses as UTC midnight and can
render as May 31 in a negative-offset timezone. That is a real bug class,
not a theoretical one.

### 3.3 `scheduled_time` is a float hour, not a time string

`14.5` means 14:30. It is a number for calendar ordering, not `"14:30"`.

### 3.4 The six categories are closed

`sightseeing | food | adventure | transport | stay | other` — CONTRACTS
§2/§8. A Stitch budget mock showing "Flights", "Hotels", "Shopping" must be
**remapped onto these six**, never added alongside them. `transport` and
`stay` are the intended homes for the first two. Use `ACTIVITY_CATEGORIES`
from `types/models.ts` for chart ordering.

Note the generated type for `amount_by_category` widens the key to
`string` (OpenAPI can't express an enum-keyed map tightly) — the backend
always returns **all six keys**, including zeros, so charts have stable
slices.

### 3.5 `401` and `403` are different, and must stay different

CONTRACTS §3: `401` = we don't know who you are → send to login.
`403` = we know, and this isn't yours → show "not yours", do **not** log
them out. `ApiError.isUnauthenticated` / `.isForbidden` exist so no screen
has to remember which number means what. Conflating them produces the
worst possible demo bug: viewing someone else's trip logs you out.

### 3.6 IDs are UUID strings

Every `id` is a UUID string, never a number. Don't `parseInt` one.

### 3.7 No trailing slashes

Routes are `/trips`, not `/trips/`. FastAPI answers a trailing-slash
request with a `307` redirect, and some clients drop the `Authorization`
header across a redirect — producing a mystery `401`. `endpoints.ts`
already has these right; don't "tidy" a slash onto one.

### 3.8 Computed stop fields are read-only

`distance_from_previous_km`, `travel_duration_hours`, `distance_source`,
`travel_gap_days`, `is_feasible` are computed per request (CONTRACTS §7.2)
and are **not** columns. The frontend displays them and never recomputes
them (CONTRACTS §8). Sending them back in a PATCH does nothing.

### 3.9 Budget totals are not on the Trip

`Trip` has `budget_target` (the cap) but no total. Totals come from
`GET /trips/{id}/budget` (ARCHITECTURE §5). A card showing "total spend"
needs that second call — plan the loading state for it.

### 3.10 Reorder is one batched call

Drag-and-drop sends the **whole** new ordering once, via
`stops.reorder([...])`. A Stitch-generated list that fires one PATCH per
row on every drag will be visibly slow and violates CONTRACTS §4.

### 3.11 CORS and the two Google keys

`CORS_ORIGINS` must contain the frontend's actual origin or every call
fails in the browser while working fine in curl.

**The two Maps keys are not interchangeable — this was verified, not
assumed.** A referrer-restricted key used server-side returns:

```
REQUEST_DENIED — API keys with referer restrictions cannot be used with this API.
```

| Var | Restriction | Consumer |
|---|---|---|
| `VITE_GOOGLE_MAPS_API_KEY` | HTTP referrer | Maps **JS** API, browser (`TripMap.tsx`) |
| `GOOGLE_MAPS_API_KEY` | IP-restricted or unrestricted — **never referrer** | Directions + Places, server-side |

Anything prefixed `VITE_` is compiled into the public bundle, so the server
key must never go there. As of now only the browser key is configured, so
the server-side Directions and Places paths are unavailable and the app
runs on its documented fallbacks (Haversine distances, local-catalog city
search). **Screens must not assume `distance_source === "directions"`.**

## 4. Auth flow (settled, so no screen improvises)

1. `auth.signup()` and `auth.login()` both return a token **and store it**.
   Signup does not need a follow-up login call.
2. `login` is an OAuth2 password flow: form-encoded, and the email goes in
   the `username` field. That's FastAPI's standard, not a mistake.
3. The token lives in `localStorage` under one key, owned by `client.ts`.
4. A `401` clears the token automatically, so the app can't get stuck
   half-authenticated.
5. Public share pages (`/share/:token`) must render with **no** token.
   "Copy this trip" requires auth — send anonymous visitors to
   `/login?redirect=/share/:token`.

the publish toggle must be **hidden or disabled for collaborators** — only

user; don't rely on catching the 403 after the fact.

**Screens 6, 10, 11, 12, 14, 15 are the demo.** If Stitch time is short,
those get the polish.

## 6. Porting Stitch output — what survives, what doesn't

Stitch emits static HTML/CSS (Tailwind-flavoured) with placeholder
content. Treat it as a **visual specification**, not as code to run.

**Keep:** layout structure, spacing, typography, color choices, component
composition, empty/loading state designs, iconography, responsive
breakpoints.

**Replace, always:**

| Stitch gives you | Replace with |
|---|---|
| Hard-coded placeholder text/data | A typed call from `endpoints.ts` |
| `<a href="...">` navigation | `<Link>` from react-router |
| `<form>` with no handler | React Hook Form + Zod |
| Its own fetch/AJAX snippets | Delete outright — `client.ts` owns HTTP |
| Its own field names | The API's names (§2 rule 5) |
| Inline `<style>` / stray CSS files | Tailwind classes |
| Its own font/CDN `<link>` tags | Bundled or self-hosted (CSP + offline) |

**Porting order per screen** — do this and a screen takes minutes:

1. Copy markup into `src/pages/<Screen>.tsx`, convert to JSX
   (`class` → `className`, self-close tags, `for` → `htmlFor`).
2. Delete every placeholder value; leave the element.
3. Import the types from `types/models.ts`.
4. Add the React Query hook calling `endpoints.ts`.
5. Bind real fields. Handle the three states the mock won't show you:
   **loading**, **empty**, **error**.
6. `npm run typecheck`.

### 6.1 Tailwind conflicts

Stitch output often assumes its own config. Rules:

- The project's `tailwind.config.js` is authoritative. If Stitch uses
  arbitrary values (`text-[#1a73e8]`), promote the recurring ones into
  `theme.extend.colors` **once**, then use the token everywhere.
- Don't paste a second Tailwind CDN `<script>` into `index.html` — the
  build already compiles Tailwind. Two Tailwinds means unpredictable
  specificity.
- If Stitch emits a design system with a different scale, adopt it wholesale
  in the config rather than mixing two scales across screens.

## 7. Phase C checklist

Run top to bottom. Everything above `—` is a hard gate.

- [ ] `cd backend && python export_openapi.py` → reports **unchanged**
- [ ] `cd frontend && npm run gen:types` → no diff in `api.d.ts`
- [ ] `npm run typecheck` → clean
- [ ] `npm run build` → succeeds
- [ ] `cd backend && python -m pytest` → green
- [ ] `docker compose up -d && docker compose exec api alembic upgrade head`
- [ ] `curl localhost:8000/health` → `{"status":"ok"}`
- [ ] Seed data loaded (`python -m app.seed`)
- [ ] Browser: no CORS errors in console on any screen
- [ ] ——
- [ ] QA Q1 critical path passes end-to-end (TASKS.md)
- [ ] QA Q2 security checks pass
- [ ] QA Q9 both fallbacks verified with keys unset

## 8. Where the seams still are

Honest list of what this rulebook does **not** de-risk:

1. ~~`alembic upgrade head` has never run against real Postgres.~~
   **Cleared.** The full chain runs from zero on a fresh PostgreSQL
   database with `alembic check` reporting no drift, plus a
   downgrade/re-upgrade round trip.
2. **Stitch's visual output may not match the 16 screens above.** Prompt it
   from §5, and check the inventory before porting anything.
3. **No frontend screen exists yet**, so the client/types in this repo are
   verified by `tsc` only — not by a rendered page. The first ported screen
   is the real test of §6; do it early and alone rather than porting all
   sixteen and discovering a systemic problem.
4. **B11's Directions path and B14 (Places search) are not built** — both
   need a server-side Google key that doesn't exist yet (§3.11). Screens
   must not assume `distance_source === "directions"`. B12 and B13 **are**
   built, so collaborators, votes, comments, and admin analytics are
   available (see §5 rows 16–17).
5. **Auto-plan output is limited by seed density** — one activity per
   category per city means a `packed` pace cannot actually fill every day.
   Cosmetic, but visible in the flagship demo.
